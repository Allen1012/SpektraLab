# 10 物理模型与色彩科学

> 用途：用中文讲清这个引擎模拟的是什么物理过程、三段核心变换怎么算、色彩在整条链路上处于什么空间，以及几条反直觉的实测结论。改任何影响画面的代码前先读这篇。

## 1. 模拟的光路

来源：`ARCHITECTURE.md` §1。

```
场景光 → [相机 + 胶片] → 潜影 → [显影] → 负片染料密度
       → [放大机 + 相纸] → 相纸潜影 → [显影] → 相纸染料密度
       → [扫描 / 观看] → 输出 RGB
```

反转片（`scan_film` 为真）没有放大机和相纸这一段，直接扫描胶片本身。

## 2. 最高原则：不要污染材质模型

> 不要为了修 rendering problem 去污染 material model。
>
> Do not pollute the material model to fix a rendering problem.

胶片和相纸配置描述的是**实测能力**，不是调节面板。具体分工：

| 需求 | 归属 | 实现 |
|---|---|---|
| 场景动态范围超出材料能分辨的范围 | 胶片**之前**的映射 | Scene Placement（设计记录 RFC-023，`filming.expose.scene_latitude`） |
| 相纸需要高光余量 | 相纸**之后**的输出端 | EDR（扩展动态范围）阶段（`scanning.edr`） |
| 最终观感 | Layer 2 | 应用内调色内核 |

修问题时找"拥有这个决定的阶段"去改，绝不改写实测响应来掩盖另一个阶段的局限。`AGENTS.md`「Do not」同样禁止改动光谱形状（81 × 5 nm）、配置数据和对数曝光轴：所有一致性校验的门槛都以它们为前提。

## 3. 三段核心变换

色彩是**光谱**的：380–780 nm，5 nm 一档，共 81 个波长。密度曲线是对数曝光 −3 到 4 上的 256 个采样。

### 3.1 RGB → 胶片曝光：Hanatos 2025 光谱上采样

`engine/src/core/hanatos.cpp`，节点 `filming.expose.upsample`。

1. RGB → XYZ（用 CAT16 色适应到胶片的参考光源）；
2. 拆成亮度 `b = X + Y + Z` 和色度 `xy`；
3. 把色度三角形变形到单位正方形；
4. 一张 192×192×81 的光谱表在**初始化时**就按胶片感光度收缩成 192×192×3 的 `tc_lut`；
5. 逐像素只是一次双三次查表再乘 `b`（内核 `spk_tc_b`、`spk_lut2d_cubic`）。

81 个波长的轴在这一步**从不碰到图像**。`tc_lut` 由 setup cache 按感光度缓存（[15](./15-engine-gpu-and-memory.md) 第 5 节）；`camera_filter` 的透过率就是乘进这个感光度里的。

### 3.2 曝光 → 密度：特性曲线、DIR 成色剂、颗粒

1. **特性曲线**（`filming.develop.curves`）：对数曝光查胶片三层的密度曲线。
2. **DIR 成色剂**（Development Inhibitor Releasing couplers，显影抑制剂释放型成色剂；`filming.develop.dir_couplers`）：一个 3×3 的"供体 → 受体"抑制矩阵作用在银密度上，经空间扩散，从对数曝光里减掉，再对反推出的曲线重新插值。它带来层间色彩分离和边缘效应。
3. **颗粒**（`filming.develop.grain`）：默认 `exact` 采样器（泊松稀疏化，精确且比 scipy 快 27 倍，RFC-002），同参数同种子可复现。

### 3.3 密度 → 光 → 响应：光谱积分

$$\text{out}_m = \sum_{\lambda} I(\lambda)\,S_m(\lambda)\;10^{-\left(\sum_k c_k D_k(\lambda) + D_{\text{base}}(\lambda)\right)}$$

算两次：

| 次 | 节点 | S（感光度） | I（光源） |
|---|---|---|---|
| 印放 | `printing.expose.enlarger_spectral` | 相纸感光度 | 放大机光源经滤色组合 |
| 扫描 | `scanning.scan_spectral` | CIE 1931 配色函数 | 观看光源 |

内核（`spk_spectral_epilogue`）把光谱轴留在寄存器里，3 个值进、3 个值出，从不为每个像素生成整条光谱。

实测配置里有 NaN（波长两端没有测量数据），参考实现让它们传播成 NaN 透过率再在 `density_to_light` 里清零；移植版在初始化时把对应 `illum_x_sens` 行清零，效果一致（陷阱 2）。

## 4. 阶段的三种性质

来源：`ARCHITECTURE.md` §3。

| 性质 | 阶段 | 形态 |
|---|---|---|
| 逐点（pointwise） | 上采样、场景宽容度、boost、曲线、两次光谱积分、色域压缩、XYZ→RGB、CCTF（色彩分量传递函数）编码 | 融合的逐元素运算；无需 halo；可做成查找表 |
| 空间（spatial） | 镜头模糊、光晕、DIR 扩散、反差蒙版、扫描模糊、锐化 | 可分离卷积；分块需要 halo |
| 随机（stochastic） | 颗粒、**眩光** | 基于计数器的随机数，可复现 |

- **眩光是默认不确定性的来源**（陷阱 1）：参考实现的眩光每次都抽一个不设种子的对数正态场，两次相同配置的渲染相差可达 0.042，比你想测的大多数差异都大。任何逐像素比较都要关掉眩光和颗粒（或用 `debug.deactivate_stochastic_effects`）。下结论说"改动弄坏了什么"之前，先把同一配置跑两次确认可复现。
- **光晕的支撑范围无界**，这是全分辨率渲染无法简单分块的原因。
- **色域压缩本身就是观感**：`gamut_compress` 是 CAM16-UCS 下的处理，亮度上是 Reinhard 肩部（70 以下为恒等），色度上对着目标空间的 `C_max` 做拐点，色相保持。亮度那一半会动到真实高光，改它就是改画面。

## 5. 色彩链路（RFC-018）

来源：`ARCHITECTURE.md` §7.5。一个工作空间，每个目的地恰好一次转换。

| # | 阶段 | 色彩空间 |
|---|---|---|
| 1 | RAW 解码（Core Image） | 线性 ProPhoto float32 |
| 2 | 引擎输入 | `io.input_color_space = "ProPhoto RGB"`，不做解码 |
| 3 | 引擎内部 | **没有 RGB 空间**：光谱 → 对数曝光 → 密度 → 打印密度 → 扫描 |
| 4 | 色域压缩 | CAM16-UCS 压进 ProPhoto RGB |
| 5 | 引擎输出 | **ProPhoto RGB，CCTF 编码**，即工作空间 |
| 6 | Layer 2、曲线、几何 | ProPhoto RGB 编码值 |
| 7a | 画布 | 图层打 ProPhoto RGB 标签，**ColorSync** 转到显示器 |
| 7b | 导出 | 一次输出变换：CAM16 压进配方的色域，再套配方的传递曲线；打标签写出，**不经 Core Graphics 转换** |
| 7c | 软打样 | 同一变换，在文件自身分辨率上 |

- **引擎内部没有 RGB 工作空间。** ProPhoto 只是输入和输出的色度定义，不是中间空间。
- **不管输入什么，输出都是 ProPhoto**，所以其他空间都是对输出的压缩，色域映射属于导出而不属于显示。
- **应用从 `open` 回复读取实际输出空间**（`Session.workingSpaceName`），从不假设（陷阱 28）。
- **唯一的取舍**：画布对超出显示器的颜色是硬裁切（ColorSync 矩阵配置文件），导出是平滑压缩；中性画面上只差 0.0012%。以文件为准。
- **TIFF 默认 Display P3**，会在调色之前不可逆地损失约 11% 色度。要继续调色的文件在配方里选 ProPhoto。
- **界面里画进画布的颜色常量也在工作空间里**（陷阱 27）：画布改成 ProPhoto γ1.8 后，原来按 sRGB 写的 `0x5F/255` 在 ROMM 里要编码成 0.29990，否则背景亮 1.478 倍。验证方法不需要"之前"的图：窗口外边距是 AppKit 自己做色彩管理的 sRGB `CGColor`，画布信箱边是着色器值经打标签的图层，两条路径必须落到同一个像素值（实拍 95 与 95.03）。`--snapshot` 不能裁判这件事，因为它在窗口层面又做了一次转换。

实现位置：`Canvas/ColourManagement.swift` 通过 `spk_output_transform` 向引擎取矩阵、CAM16 常数和 `C_max` 表，按（源，目标）缓存；应用里没有第二套色彩库。`Import/ImageDecoder.swift` 手工构造线性 ROMM 空间（D50 原色）作为解码目标。

## 6. 三种白平衡在三个阶段

| 名称 | 阶段 | 单位 / 方式 |
|---|---|---|
| Camera 的色温、色调 | 解码（`CIRAWFilter`），改动要重新解码 | 开尔文 |
| 放大机滤色组合 | 印放，Solve 解算中性值，Y/M 偏移在其上 | CC，应用的偏移比例为 40 |
| Post-Dev 的白平衡 | Layer 2，作用在扫描结果上 | 应用内核 |

## 7. 反直觉的实测结论

### 7.1 曝光补偿移动的是负片，不是相纸亮度（陷阱 30）

2026-09-21 用发布版 dylib 在中性灰阶上实测：

| | Y(0)：用 `exposure_compensation_ev` | Y(0)：把同样增益乘在输入上 |
|---|---:|---:|
| −2 EV | 0.17332 | 0.01862 |
| 0 EV | 0.17563 | 0.17563 |
| +2 EV | 0.17309 | 0.58430 |

在负片上（`scan_film: true`）两条路径逐位相同；抵消发生在印放侧，而且是有意的：`core/printing.cpp` 用 `kMidgray × 2^exposure_compensation_ev` 算放大机增益，就像暗房师傅会按底片曝光重新定印放时间。所以**曝光补偿改变的是场景落在胶片特性曲线的哪一段**（反差、趾部和肩部的介入程度），而不是相纸亮度；±6 EV 时中灰仍在 0.175 附近，反差却塌了，这就是它的特征。改相纸亮度的控件是 `enlarger.print_exposure`（0.5 → Y(0) 0.535，2.0 → 0.025）。

做实验时，用曝光补偿当亮度对照等于什么都没测；应该在输入上预乘增益。

> 产品侧的例外：应用打开会话时带 `product_defaults: true`，引擎因此把 `print_exposure_compensation` 设为 false（`engine.cpp` `apply_product_defaults`），让应用里的相机曝光补偿真的能改变成品亮度，因为 SpektraLab 没有"印放自动补偿"开关。上表是参考行为（不带 `product_defaults`）。

### 7.2 色彩在趾部比影调先消失（陷阱 31）

`kodak_portra_400` + `kodak_portra_endura` 默认参数，同一色度放在不同场景曝光下渲染，测相纸的 C\*ab：

| 场景 EV | −5 | −4 | −3 | −2 | −1 | −0.5 | 0 | +1 | +2 | +3 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 肤色 | 1.6 | 1.1 | 3.9 | 14.1 | 22.3 | **24.5** | 23.7 | 21.2 | 14.2 | 5.3 |
| 植物 | 1.5 | 0.9 | 1.9 | 12.1 | 29.1 | 38.5 | 47.0 | **56.1** | 51.8 | 35.7 |

**低于约 −3.5 EV 时一切都渲染成 C\*ab ≈ 1.7 的灰，而不是暗的彩色。** 以峰值的 50% 为界，色彩窗口约 4.2–4.4 档，而同一组合按 ISO 6846 的影调窗口是 5.66 档。所以问"这个介质能容纳几档"时必须说清是哪种宽容度；把阴影拉到色彩边界和影调边界之间，只会得到更亮但仍然灰的区域，乳剂没记录下颜色，下游什么也找不回来。探测脚本：`rfc/probes/rfc023-slm-probe.py`。

### 7.3 印放平衡用 sRGB 灰来定（陷阱 21）

参考实现计算印放平衡时调用 `_rgb_to_film_raw(rgb)` 没传色彩空间，于是用了默认的 sRGB，而不是 `io.input_color_space`。看着像疏忽，但它决定了平衡。移植版**有意**复现为 `core/printing.hpp` 的 `kMidgrayProbeColourSpace`；改用输入空间会让 93% 的画面移动 2 个码值，一致性校验也会变红。"修"它之前先想清楚哪边才是错的。

### 7.4 光谱上采样在紫色上有结构性盲区（陷阱 13）

RGB → 光谱 → XYZ → RGB 往返在每个色相上都有 1.7–3.8 dE 误差，紫色最差（平均 3.07，并向蓝色偏转约 6°）。用三个数重建光谱本身欠定，平滑光谱先验又对非光谱色需要的双峰光谱估计不足。这是结构性的，不是缺陷，也是为什么配置好的相机查找表（LUT）在这些色相上能胜过光谱重建。

### 7.5 外部软件导出的文件不是场景线性的（陷阱 11、12）

- 引擎是一台"相机"，需要场景线性辐射。外部文件最难的部分在这道边界上，不在物理模型里。
- 外部 RAW 软件里的曝光调整在有色调曲线时不是增益：Capture One 的 +1 EV 导出后中位比值是 ×1.57，不同影调间差 1.8–2.1 倍；切到 Linear Response 后是 ×2.09，差 1.17 倍。
- 外部解码不可逆：不同软件给出不同的场景估计，从而是不同的胶片观感。所以 SpektraLab 把解码作为产品契约的一部分，自己用 Core Image 解 RAW，而不做适配层。
- 2026-08-26 有三个色彩 bug 在 750 个测试通过的情况下同时存在，因为所有测试输入都是线性的。测色彩要测**不变性**（同一含义、不同表示 → 相同渲染），而不是参考图（RFC-010）。
