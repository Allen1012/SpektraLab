# 09 设计决策记录

> 用途：用架构决策记录（ADR）的格式整理已经落地或明确拒绝的关键决策，回答"为什么不那样做"。每条注明出处，原文细节见 [14](./14-rfc-index.md) 索引里的设计记录（RFC）。

格式：**状态** / **背景** / **决策** / **原因** / **影响与后续**。

---

## ADR-01 一个进程，引擎经手写 C 接口编译进应用

- **状态**：已实施（RFC-014，2026-09-10）。
- **背景**：最初的引擎是 Python（numba/MLX），作为子进程服务通过 stdio JSON-RPC 与 SwiftUI 前端通信；大像素靠工作目录里的文件交接（CONTRACT §1）。打开 45 MP 要约 7 s，一次重印约 190 ms，部署要带 Python 环境。
- **决策**：把引擎改写成 C++20 + Metal，**编译进应用目标**；边界是手写的 `extern "C"` 接口 `spk_engine.h`；参数仍用 JSON，像素用共享缓冲进、零拷贝纹理出。运行时没有 Python、子进程、管道。
- **原因**：C 二进制接口（ABI）稳定、面窄，并且能被 `ctypes` 调用，所以一致性校验能直接驱动要发布的二进制（`ARCHITECTURE.md` §8.2）。没有选 Swift 的 C++ 互操作，正是因为它不能做到后一点。
- **影响**：45 MP 全分辨率 0.87 s，live 重印约 0.01 s。方法名、字段名、档位名、版本号都保留了旧服务的名字，`transport_version`/`schema_version` 仍为 1。上游 Python 只作为校验的参考答案存在（[16](./16-parity.md)）。旧的 `native/` stdio 代理宿主被有意不带过来（`AGENTS.md`）。

## ADR-02 引擎只返回像素，从不写文件

- **状态**：已实施（`ARCHITECTURE.md` §8.8）。
- **背景**：Python 时代的 `export`、`export_di`、`preview_stock_lut` 都在服务里写文件。
- **决策**：引擎返回像素和烘焙好的表；TIFF、JPEG、PNG、`.cube`、打印预览全部由 `Export/Exporter.swift` 通过 ImageIO 写出。
- **原因**：ImageIO 已经会写这些格式，并且负责色彩标签；引擎里再写一套就有两处决定"文件是什么颜色"。
- **影响**：导出 = `spk_reprint(full)` + 应用侧 Layer 2、几何、缩放、输出变换 + ImageIO。数字中间片（DI）的 TIFF 是设备 RGB、不带配置文件。写文件采用"先写隐藏的 `.partial` 再移动"，崩溃不会留下半个文件。

## ADR-03 ProPhoto RGB 作为唯一工作空间，每个目的地只转换一次

- **状态**：已实施（RFC-018，2026-09-13）。
- **背景**：引擎曾在 `spk_open` 里写死输出 Display P3，而头文件声明的默认值是 sRGB，两者不一致；导出要从显示空间再转一次，丢色。
- **决策**：引擎输出 ProPhoto RGB（CCTF 编码）作为工作空间；Layer 2、曲线、几何都在这个空间里；画布打 ProPhoto 标签交给 ColorSync；导出用 `spk_output_transform` 取的数据做一次 CAM16 色貌模型下的色域压缩 + 配方传递曲线。
- **原因**：不管输入什么，输出都是同一个大空间，其他空间都只是它的压缩，色域映射属于导出而不属于显示；转换数据来自引擎自己的色彩数据，应用里不需要第二套色彩库。
- **影响**：应用必须从 `open` 回复读取工作空间（陷阱 28）；所有画进画布的界面颜色常量都要按工作空间编码（陷阱 27）；画布对超色域颜色是硬裁切，导出是平滑压缩，差异 0.0012%，以文件为准；TIFF 默认 Display P3 会损失约 11% 色度。

## ADR-04 两层参数：Layer 1 在引擎，Layer 2 在应用

- **状态**：已实施（`ARCHITECTURE.md` §7.2）。
- **背景**：滑块是否跟手，取决于它改的东西要不要跑引擎。
- **决策**：胶片、相纸、相机、放大机、场景定位属于 Layer 1，改动发 `params_delta`；曝光、曲线、色彩平衡、扫描后白平衡属于 Layer 2，由应用自己的 Metal 内核做，从不离开应用。几何（裁切、旋转）也在引擎之后，除非片边让裁切进入底片。
- **原因**：Layer 2 亚毫秒、Layer 1 约 14 ms 起。"不要污染材质模型"也要求最终观感放在 Layer 2，而不是去改胶片配置（[10](./10-physical-model-and-colour.md) 第 2 节）。
- **影响**：每个线上字段都标 shoot 或 print；字段名由 `FilmParams.wire` 唯一定义，并由测试固定。

## ADR-05 分辨率只有两个状态：预览和原图

- **状态**：已实施（2026-09-12，`ARCHITECTURE.md` §7.3）。
- **背景**：以前有一个随缩放切换的"档位阶梯"，画面会在缩放时换档，日志里是 `detail preview 3400x2266 landed`。
- **决策**：所有交互编辑都在用户选的预览长边上渲染（引擎 `live` 档，默认 2560）；编辑停下 400 ms 后跑一次原分辨率渲染，落地后显示。缩放不选档。
- **原因**：简单、可预测；原分辨率渲染已经快到不到 1 秒，阶梯的意义消失。
- **影响**：同一时间只有一次全分辨率渲染；放大超过预览长边时画面会软，直到原图落地（`preview` / `full` 标记）。文档曾在阶梯删掉五天后还在描述它，是被一张截图里 33% 缩放下的 `full` 标记戳穿的（`AGENTS.md`）。

## ADR-06 保守的 live 字段集合

- **状态**：已实施（API-SPEC §10.2，`core/params.cpp` `is_live`）。
- **背景**：在现有流水线上原地改参数最快，但构造时推导的状态（印放平衡中灰、反转片拓扑、被剪掉的恒等节点）会变陈旧。
- **决策**：只有 `print_exposure`、两个滤色偏移、`preflash_exposure`、`filter_shift_scale` 和三个条带设置原地修改；其余字段一律重建流水线。
- **原因**：重建实测只要约 18.8 ms，保守几乎免费；缓存底片和 setup cache 都在重建中保留。
- **影响**：扩大 live 集合前，必须对每个新字段重跑"重印等于完整渲染"的校验。

## ADR-07 着色器由 `build.sh` 用安全数学编译，启动时探测

- **状态**：已实施（RFC-014 §5.1、`ARCHITECTURE.md` §8.4）。
- **背景**：Xcode 26.6 的 `MTLCompileOptions` 和离线编译器默认都是快速数学；应用为画布设了 `MTL_FAST_MATH = YES`。快速数学让 `exp` 和 fma 收缩漂移最多 1.1e-5，超过 float32 容差且无声无息。
- **决策**：内核不进 Xcode 目标，由 `engine/build.sh` 用 `-fmetal-math-mode=safe -fmetal-math-fp32-functions=precise` 编译；`spk_engine_create` 用 `spk_math_probe` 实测，发现快速数学就拒绝启动；`check_math_guard.sh` 证明守卫会触发。
- **原因**：构建参数是那种"会没人再读"的守卫，所以要在运行时问 GPU 实际编译了什么。
- **影响**：改 `.metal` 后要跑 `build.sh metallib`/`bundle`；不要删安全数学参数，也不要把内核挪进 Xcode（`AGENTS.md`「Do not」）。

## ADR-08 引擎资源入库，并在产物上检查

- **状态**：已实施（`ARCHITECTURE.md` §5）。
- **背景**：资源（约 15 MB 常量、配置、查找表）只能用上游 Python 烘焙。
- **决策**：`engine/resources/` 入库，全新检出无需烘焙即可构建；只有 metallib 不入库。构建前脚本检查资源和许可证文本是否齐全；`build.sh bundle` 同步进应用。
- **原因**：构建应用不应依赖一个外部 Python 环境。
- **影响**：静默失败的形态从"缺失"变成"陈旧"（陷阱 14），所以要对已构建 `.app` 里的资源再跑一次校验。

## ADR-09 Xcode 工程由脚本从文件系统生成

- **状态**：已实施（`Tools/gen-project.py`）。
- **背景**：手维护 `project.pbxproj` 容易漏文件，多个工作树合并时冲突。
- **决策**：工程文件由脚本生成，包括引擎的 C++ 编译单元；对象 id 取文件**相对于工程**路径的 sha1；版本号只在脚本里定义。
- **原因**：以前用绝对路径哈希，工作树和主检出生成的文件只有 1400 个 id 不同，任何合并都在双方都没改的地方冲突。
- **影响**：增删任何源文件后必须重跑生成器；漏了 `.cpp` 报链接错误，漏了 `.swift` 报 `cannot find X in scope`。

## ADR-10 内存：应用记账不拥有，引擎主动归还，磁盘缓存托底

- **状态**：已实施（RFC-019、RFC-020；`ARCHITECTURE.md` §4）。RFC 文件头仍写"提案"。
- **背景**：一张 102 MP 哈苏 16 位 RAW 在 24 GB 机器上吃到 23 GB（RFC-020 §0）。
- **决策**：
  - 应用侧 `MemoryArena` 登记每块大内存及驱逐回调，受"给系统的余量"和"应用上限"约束；
  - 引擎侧缓冲池在换帧、内存压力、空闲 60 秒时回收，死缓冲销毁而不只是回池，源图和缓存底片用文件映射；
  - 内存之下是一个 SQLite 索引、GDSF（贪心双重大小频率）淘汰的磁盘缓存；
  - 同时只有一次全分辨率渲染，导出一次一帧。
- **原因**：记账和拥有分开，各组件保持自己的生命周期；文件映射让同一平面的 `phys_footprint` 从 1362 MB 降到 137 MB。
- **影响**：102 MP 峰值从 23 GB 降到 13.7 GB（1.0.3）。条带执行器已实现但应用未开启，按空闲内存动态选条带高度留给后续（RFC-020 §7）。

## ADR-11 每帧只测一次光，所有档位共用

- **状态**：已实施（RFC-015 P.1，CONTRACT §6 2026-09-12）。
- **背景**：每档各自测光，导出与用户认可的画布曝光不同，真实 RAW 上相差可达 +0.069 EV。
- **决策**：会话在 1600 px 缩图上（经输入解码和几何之后）测一次光，七种方式都算好，每档都用同一个 EV；缓存键是测光节点上游的字段。
- **原因**：导出必须和画布一致；测光分辨率独立于档位，改预览分辨率不会移动自动曝光。
- **影响**：换胶片、改曝光补偿、换测光方式都不重测（45 MP 上重测只要 21 ms）。

## ADR-12 解码是产品契约的一部分

- **状态**：已实施（陷阱 12，`Import/ImageDecoder.swift`）。
- **背景**：外部软件导出的文件带色调曲线和各自的相机配置，既不是场景线性的，也不可逆；不同软件给出不同的胶片观感。
- **决策**：应用自己用 Core Image 解 RAW，关掉 Apple 的色调渲染，得到线性 ProPhoto float 交给引擎；同时解一份显示用的"原图"。不做针对外部软件的适配层。
- **原因**：引擎是一台"相机"，需要场景线性辐射；固定解码才能固定观感。
- **影响**：相机白平衡和镜头校正属于解码，改它们要重新解码；色彩测试必须覆盖编码输入（陷阱 11）。

## ADR-13 三个入口一套实现，agent 默认关闭

- **状态**：已实施（RFC-026，1.1.1）。
- **背景**：希望 agent 能脚本化地编辑照片，但不希望出现第二套实现，也不希望默认就能被本机任意进程驱动。
- **决策**：窗口、`SpektraLab cli`、`SpektraLab mcp` 是同一个二进制里的同一个 `Session`；工具表 `AgentTools` 只有一份，命令行（CLI）和 MCP（模型上下文协议）是它的两种编码；agent 只编辑参数，不生成图像内容；访问开关 `ui2.agentAccess` 默认关闭，每次调用重读；补丁整体校验后才应用。
- **原因**：一套实现就没有漂移；默认关闭是 stdio 无认证下唯一的保护。
- **影响**：批量导出期间只放行只读工具；没有路径白名单（[02](./02-architecture.md) 第 7 节）。

## ADR-14 批量导出串行，并锁住当前帧

- **状态**：已实施（`ARCHITECTURE.md` §7.8，陷阱 34，2026-09-26）。
- **背景**：导出器写的是"当前打开的帧"；曾有点击或 agent 调用在 `select` 和写文件之间换了帧，把一帧的渲染写进另一帧的文件名。
- **决策**：批量导出就是一个"选中 → 冲洗 → 导出 → 下一帧"的循环，没有队列、没有并行、没有数据库；运行期间 `batchExporting` 让所有改变当前帧的操作失效。
- **原因**：两次 100 MP 全分辨率渲染放不进内存；串行的峰值是一次渲染而不是 N 次。
- **影响**：新增任何代替用户改变当前帧的操作都要检查 `batchExporting`；`select` 自己不能检查。

## ADR-15 sidecar 不放在照片旁边

- **状态**：已实施（`06847ab`，2026-09-13，陷阱 35）。
- **背景**：照片旁的 `<image>.spektra.json` 会污染用户的图库，而且照片可能在只读位置。
- **决策**：sidecar 放在 `~/Library/Application Support/SpektraLab/Sidecars/`，以"文件名 + 路径 SHA-256 前 16 位"命名，带文件指纹以识别移动过的文件；旧位置的文件在第一次读到时迁移。
- **原因**：除了导出，应用不往用户文件夹写任何东西。
- **影响**：测试打开测试图片前要先复制（冲洗会写 sidecar）；在照片文件夹里找 sidecar 只能找到残留。

## ADR-16 一致性门槛按实测定在 3e-5

- **状态**：已实施（RFC-014 §8.3）。
- **背景**：端到端 21 个节点的 float32 累积误差大于单节点的存储精度。
- **决策**：绝对门槛 3e-5（已验证的 Python Metal 核心是 1.9e-5，C++ 引擎是 2.3e-5），配一个"一个 16 位码值"的门槛防止系统性偏移。
- **原因**：门槛要测得出来，而不是任何 GPU 路径都达不到的 epsilon。
- **影响**：不要收紧到 epsilon，也不要在没说明测量依据时放宽（[16](./16-parity.md) 第 4 节）。

## ADR-17 有意保留或背离参考实现的行为

- **状态**：已实施（RFC-014 §8.5，陷阱 21、22）。
- **决策**：印放平衡用 sRGB 灰（`kMidgrayProbeColourSpace`）**有意复现**；`lens_blur_um` 在 C++ 里生效，**有意背离**；输出色彩空间默认值有意不同。每条都登记在校验脚本里，两边若某天一致了反而失败。
- **原因**：差异要有名字、有理由、能被测试，而不是悄悄继承或悄悄修掉。

## ADR-18 未定稿的功能用编译期开关撤下，而不是删除

- **状态**：已实施（`Model/FeatureFlags.swift`）。
- **背景**：局部蒙版的交互设计还没定（用户在写产品需求文档，即 PRD）；反差蒙版"背后还有问题"（2026-09-29）；黑白缺镜头滤镜和号数控件。
- **决策**：代码保留，开关关闭：`masks = false` 时已有蒙版的 sidecar 照常读写但不生效；`toneMask = false` 时线上永远发 `contrast_mask_active = false`；`blackAndWhite` 自 1.3.3 起打开。每个开关都写明谁决定、什么条件下翻转。
- **原因**：删掉丢工作，上线又会让用户学会一个马上要变的形态；开关同时保住代码和诚实。
- **影响**：`enlarger` 开关当前没有任何引用，Enlarger 分区总是显示（[03](./03-core-modules.md) 第 6 节）。

## ADR-19 数字中间片取代旧的"DI 包"

- **状态**：已实施（RFC-028，2026-09-29）。
- **背景**：旧的 DI 包是"按印放表密度轴归一化的负片 + `.cube`"，与所选相纸耦合。
- **决策**：产品的数字中间片是去片基、在胶片自身中性曲线上反转、按 Kodak Cineon log 编码的正像，16 位 TIFF、不带色彩标签，旁边放两个查看用 `.cube`。旧接口 `spk_export_di` 保留给校验脚本和求解器读底片，应用不再使用。
- **影响**：反转片没有 DI；片边画布的 DI 齿孔没有切口效果（[04](./04-render-flow.md) 第 10 节）。

## ADR-20 发布用 ad-hoc 签名的 zip

- **状态**：已实施（用户决定，`AGENTS.md`「Conventions」、`ARCHITECTURE.md` §5）。
- **决策**：强化运行时、空权限、ad-hoc 签名，以 GitHub 预发布 zip 分发，说明里附去隔离命令。**不用 Developer ID，不要再提议。**`package.sh` 保留完整的公证路径，供将来使用。
- **影响**：用户首次运行要执行 `xattr -d -r com.apple.quarantine /Applications/SpektraLab.app`。
