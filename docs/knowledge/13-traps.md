## 1. 渲染正确性

### 陷阱 1：流水线默认是不确定的

参考实现的眩光每次调用都抽一个**不设种子**的对数正态场，`print_render.glare` 默认打开。两次相同配置、相同后端的渲染能相差 **0.042**，比你想测的大多数差异都大。C++ 引擎里眩光的种子也是每次渲染新抽的（`pipeline.cpp` `print_prefix`，`fresh_seed()`）。

颗粒看似随机其实不是：`exact` 采样器从固定的种子序列派生每一块的随机流，跨运行、跨线程数都可复现。

**任何逐像素比较都要同时关掉眩光和颗粒**（或 `debug.deactivate_stochastic_effects = True`），关掉后整条流水线逐位可复现。这条曾让人追了一个小时不存在的移植 bug。**下结论说改动弄坏了什么之前，先把同一配置跑两次，确认能复现。**

### 陷阱 2：实测配置里有 NaN

Portra 400 的 `channel_density` 有 22 个 NaN、`base_density` 有 20 个；Portra Endura 的 `channel_density` 有 22 个。它们标记没有测量数据的波长，多在紫外和红外两端。参考实现让它们传播成 NaN 透过率，再在 `density_to_light` 里清零；任何替代实现都必须复现这一点。移植版在初始化时就中和它们：把受影响的 `illum_x_sens` 行清零（`prepare_spectral_constants`），内核里不加分支。

### 陷阱 8：近似一个分布可以保住 RMS，却改变观感

`fast_stats` 把颗粒的 RMS 颗粒度复现到 0.14% 以内，却把**每个密度下的偏度都压成 0**。偏度是 `1/sqrt(mu)`，`mu` 随密度上升，所以偏度编码的是胶片暗部与亮部颗粒的不同性格（暗部 +0.165，亮部 +0.022）。二阶矩一致不能证明噪声模型等价，要查三阶矩。默认用 `exact` 采样器（泊松稀疏化，精确，比 scipy 快 27 倍）；`use_fast_stats` 只用于预览（设计记录 RFC-002 §3.4）。`parity_grain.py` 因此同时检查均值、标准差和偏度。

### 陷阱 9：颗粒抽样是独立同分布的，分块不会产生接缝

逐像素抽样没有空间相关性，分块只会得到另一个实现，不会有边界伪影。接缝只来自模糊（颗粒模糊、微结构），分块时需要约 4 px 的 halo。不要因为怕接缝而不分块抽样；也不要不带 halo 就分块做模糊。C++ 条带执行器因此在每次渲染只抽一个种子，并让邻域阶段携带 halo（[04](./04-render-flow.md) 第 7.3 节）。

### 陷阱 19：释放不等于空闲

缓冲的最后一个句柄释放时，只说明**以后**不会有派发再引用它，不说明已经编码进打开的命令缓冲、还没执行的派发不会用它。把它交给下一次 `alloc`，就让后面的内核覆盖了前面内核还没读的缓冲：**27 个渲染一致性用例错 25 个，没有崩溃，没有报错。**

释放的缓冲在 `flush` 时才变为可复用，所以流水线在节点边界 flush，也正是参考实现求值的位置。**如果你发现自己为了速度在删这些 flush，你删掉的就是这个。**详见 [15](./15-engine-gpu-and-memory.md) 第 2 节。

### 陷阱 20：移植过来的内核对矩阵方向的约定不一致

`spk_tc_b` 和 `spk_cam16ucs_compress` 要普通行主序矩阵（`out[i] = Σ m[3i+j]·x[j]`）；`spk_matmul3` 和 `spk_cctf_encode_matrix` 要**转置**的。两者对各自来源的 Python 调用点都是对的：`tc_b_matrix` 本来返回的就是 `RGB_to_XYZ(eye).T`，而 `XYZ_to_RGB(eye)` 是原样传入的。弄错时红通道均值偏 +0.14、蓝通道偏 −0.08，看起来像调色决定而不像 bug。`pipeline.cpp` 有专门的 `row_major()` 和 `transposed()` 辅助函数，请用它们。

### 陷阱 21：印放平衡用 sRGB 灰来定

参考实现的 `FilmingStage._simple_rgb_to_density_spectral` 调用 `_rgb_to_film_raw(rgb)` 时没传 `color_space`，于是取了默认值 **sRGB**，而不是 `io.input_color_space`。不管帧用什么编码，每张打印的曝光都是对着 sRGB 灰归一化的。看着像疏忽，也许确实是，但它决定了平衡。移植版**有意**复现为 `core/printing.hpp` 的 `kMidgrayProbeColourSpace`；改用输入空间会让 93% 的画面移动 2 个码值。如果你要"修"它，预期一致性校验会变红，并认真想想哪一边才是错的。

### 陷阱 22：两个线上参数的含义和 schema 说的不一样

- **`camera.lens_blur_um` 在 Python 引擎上不起作用。** `_build_topology` 用 `pixel_size_um` 推导 sigma，而它在第一次渲染前是 `None`，所以节点总被剪掉。实测 `max |out(0) − out(50 µm)| == 0.0`。C++ 引擎每次运行时计算 sigma，所以参数生效。这是有意的差异，两者若哪天一致了，`parity_render.py` 反而失败。
- **`dir_couplers_amount` 超过约 1.736**（在 kodak_portra_400 上二分得到）时，成色剂逆运算自身的曝光轴不再单调，而 `np.interp` 要求递增的 `xp`。超过这个值，参考实现的输出是 numpy 内部搜索的产物，不是模型的。**协议允许到 4.0**，schema 的范围比数学支持的宽。

### 陷阱 23：一致性校验全绿不等于画面正确

移植中的六个真实 bug 里有两个不在任何校验脚本的覆盖范围，因为脚本直接把 numpy 数组交给引擎，从不经过应用自己的文件读取：`readLinearRGB` 里的**上下翻转**（冲洗正确、上下颠倒，27 个用例全绿），以及**结果纹理归帧内存池所有**、调用方还没画就被释放。现在由 `testTheFrameIsReadTopRowFirst` 和 `testEachTierRendersAtItsOwnResolution` 固定。**要看截图。**`--snapshot` 很便宜，而且是唯一能看到用户所见的检查。

## 2. 内存、性能与测量

### 陷阱 6：float16 不是免费的

fp16 最小的次正规数约 5.96e-8，所以 `log10(max(raw, 0) + 1e-10)` 里的 `1e-10` 会下溢成 0，`log10(0)` 得到 `-inf`。光谱内核上实测 fp16 存储误差为相对 2.7e-3。而且 fp16 **并不更快**（6.9 ms 对 6.8 ms）：这些内核受计算限制，不受带宽限制。macOS 上用 float32。（C++ 引擎的工作精度是 float32；常量文件里 Hanatos 光谱以 float16 存储，只作初始化数据。）

### 陷阱 17：这台机器不是基准

这里的计时经常被大幅污染。2026-09-10 一次预热后的 `service.open` 读到 1.86–2.81 s，而几小时前是 922 ms，原因是**后台的《文明 VI》占着 GPU、CPU 125%**，负载 6.2。同一个没改动的提交曾在几小时内测出 23.3 s 和 18.9 s。

- 相信一个数字之前看 `ps -Ao %cpu,comm -r | head` 和 `uptime`，并在引用它的消息里说明。
- **交替测量**，不要先后测量：在同一个会话里轮流跑两组。
- 问题关乎导入或分配而不是 GPU 时，优先看 CPU 时间。
- `core=native-metal` 和正确性结果与计时无关，分开报告；这样即使会话被污染也还有用。

### 陷阱 18：渲染慢不是退回了 CPU，已测到三个原因

45 MP 全分辨率渲染约 13 s，恰好和 numba 的数字一样，于是被读成"根本没启用 Metal"。**引擎里没有可退回的 CPU 路径。**三个独立原因，任何一个都可能复发：

1. **帧内缓冲不复用**：只在帧末回收，峰值变成所有中间结果之和：24 MP 时约 11 个 288 MB 缓冲，一个命令缓冲让 3.2 GB 同时驻留，**6.4 s 而不是 0.4 s**。现在缓冲按引用计数（`gpu::BufferRef`）。
2. **初始化缓存没移植**：Python 有三个（`_SETUP_CACHE`、`_OUTPUT_CMAX_CACHE`、`filming_tc_lut_memory`），移植版一个都没有，于是 live 集合以外的每个参数都要重算 46,080 单元的 `C_max` 表和 192×192×81 的 `tc_lut`：每个滑块 160–250 ms。见 `core/setup_cache.hpp`。
3. **打开路径上的整帧拷贝**：Swift 在 `-Onone` 下逐像素去 alpha；源图既留在主机又按档上传。打开 24 MP RAW 要 5.9 s，现在 2.0 s。

下理论之前：先看 `core=native-metal`，再分别计时三个档位，再看**重复**渲染时的峰值内存；缓冲池在增长就是信号。

## 3. 色彩与输入

### 陷阱 11：色彩 bug 是无声的，而一致偏斜的测试套件会报告十足的信心

2026-08-26 有三个色彩 bug 同时存在，而 **750 个测试全部通过**：`input_cctf_decoding=True` 在融合路径上报错、服务把它写死成 False、`auto_exposure` 把增益乘进了伽马编码的数据（等效增益 `g ** 1.8`）。没有一个崩溃，两个产出的是**看起来合理的照片**。它们活下来，是因为**仓库里每个测试和基线喂的都是线性输入**，Capture One、Lightroom、Photoshop 实际导出的编码整型文件从来没被测过。套件不是弱，而是一致地偏斜，这更糟：它在一无所知的时候报告了信心。相信色彩结果之前，问一句测试的**输入**有什么共同点。测**不变性**（同一含义、不同表示 → 相同渲染），而不是参考图（RFC-010）。

### 陷阱 12：输入契约才是产品真正出问题的地方

引擎是一台"相机"，需要场景线性辐射。外部文件的难处全在这道边界上，不在物理上。

- **`decode_input` 在门口运行**（`preprocess.decode_input`），之后一切都是线性的。不要把传递函数挪回 `upsample` 里，那正是 `g ** 1.8` 曝光 bug 的成因。
- **外部 RAW 软件里的曝光调整在后面有色调曲线时不是增益。** Capture One 上实测：+1 EV 导出后中位比值 ×1.57，不同影调间差 1.8–2.1 倍；把曲线设为 **Linear Response** 后是 ×2.09、差 1.17 倍，自动曝光能吸收它（dE 13.7 → 0.94）。
- **外部解码不可逆。** 相机配置文件（C1 的 ProStandard、Adobe 的、dcraw 的矩阵）无法从导出的 TIFF 恢复，两个软件给出两种场景估计，也就是两种胶片观感。把解码作为产品契约的一部分固定下来，不要做适配层。

### 陷阱 13：光谱上采样在紫色上有结构性盲区

`RGB → 光谱 → XYZ → RGB` 往返在**每个色相**上都有 1.7–3.8 dE 误差，紫色最差（平均 3.07，向**蓝色**偏转约 6°）。用三个数重建光谱本来就欠定，平滑光谱先验又对非光谱色需要的双峰光谱估计不足。这是结构性的，不是缺陷，也是为什么配置好的相机查找表（LUT）在这些色相上能胜过光谱重建：它从不构造光谱。不看颜色就不要放宽这些界限。

### 陷阱 27：画进画布的每个界面常量都在工作空间里

画布纹理保存的是**画面**的色彩空间，而应用把自己的界面元素（画面四周的信箱边、蒙版叠加层的红色）也画进去。这些按 sRGB 码值写的常量，在纹理还是 Display P3（传递函数与 sRGB 相同）时是对的。RFC-018 把画布改成 ProPhoto RGB（γ1.8）后，同样的数字就是另一种颜色：背景 `0x5F/255` 是线性 0.11444，在 ROMM 里要编码成 **0.29990**；不改的话四周会多出 **1.478 倍**的光，整个界面都会在照片周围偏移。

**不需要"之前"图的检查**：窗口外边距是 AppKit 自己做色彩管理的 sRGB `CGColor`，画布信箱边是着色器值经打标签的图层，两条路径通往同一个灰，必须落在同一个像素上：实拍读数 **95 和 95.03**，用原始常量时约 113。`--snapshot` 不能裁判这件事：`cacheDisplay` 会按图层标签再做一次窗口级转换，离屏对比的是两种转换而不是两种渲染，连没动过的区域都不一样。

### 陷阱 30：曝光补偿移动的是负片，不是相纸

中性灰阶实测（2026-09-21，发布版 dylib）：用 `exposure_compensation_ev` 时 −2/0/+2 EV 的 Y(0) 是 0.17332/0.17563/0.17309，把同样增益乘在输入上是 0.01862/0.17563/0.58430。负片上两者逐位相同；抵消在印放侧，而且是有意的：`core/printing.cpp` 用 `kMidgray × 2^exposure_compensation_ev` 算放大机增益，相关的两个开关在 `params.hpp` 里写死为 true、不在协议上、只有 `debug.lut_mode` 会清掉。放大机按胶片曝光重定印放时间，就像暗房师傅那样。

所以**曝光补偿改变的是场景落在胶片特性曲线的哪一段**（反差、趾部、肩部），不是相纸亮度；±6 EV 时中灰仍在 0.175 附近而反差塌了，这就是特征。改相纸亮度的是 `enlarger.print_exposure`（0.5 → 0.535，2.0 → 0.025）。**做实验时用曝光补偿当亮度对照等于什么都没测**，应在输入上预乘。RFC-023 §15.4 因此丢过一组对照。

> 补充：应用打开会话时带 `product_defaults: true`，引擎因此关掉 `print_exposure_compensation`，让应用里的相机曝光补偿真的改变成品亮度（[10](./10-physical-model-and-colour.md) 第 7.1 节）。

### 陷阱 31：色彩在趾部比影调早得多就消失

同一色度放在不同场景曝光下渲染（Portra 400 + Portra Endura，默认参数），**低于约 −3.5 EV 时一切都渲染成 C\*ab ≈ 1.7，是灰而不是暗的彩色**。以峰值的 50% 为界，色彩窗口约 4.2–4.4 档，而同一组合的 ISO 6846 影调窗口是 5.66 档。所以问"这个介质能容纳几档"必须说清是**哪种**；把阴影拉到色彩边界和影调边界之间，只会得到更亮但仍然灰的区域：乳剂没记录下颜色，下游什么也找不回来。数据表见 [10](./10-physical-model-and-colour.md) 第 7.2 节，探测脚本 `rfc/probes/rfc023-slm-probe.py`。

## 4. 协议、数据与持久化

### 陷阱 14：渲染用的是应用解析到的那份**数据**

旧版本这条讲的是 `PYTHONPATH` 和可编辑安装，随服务一起消失了：引擎编译进二进制，渲染用的**代码**不再有歧义。同样的失败模式下移了一层，到了数据上。`EngineClient.defaultResources()` 有一个"往上找源码树的 `engine/resources`"的回退，给从源码树运行的构建用，而它会说谎：资源从没同步过的构建会高高兴兴地用上层检出里的资源渲染。

- `engine/build.sh bundle` 负责同步；应用目标的构建前阶段 `Tools/check-bundle-resources.sh` 在资源缺失时让构建失败，所以静默的情况是**陈旧**而不是缺失。
- `EngineResourceOriginTests` 断言资源来自应用包内。

> 与英文文档的出入：原文写查找顺序是"先应用包，再 `SPEKTRAFILM_ENGINE_RESOURCES`，再往上找源码树"；**代码实际是环境变量优先**，然后应用包，然后往上找（`Service/EngineClient.swift` 第 221–239 行，[05](./05-engine-boundary.md) 第 6 节）。

这个 bug 的最初版本花掉了整整一个会话：GPU 核心在应用检出没有的分支上，每次渲染都跑在 numba 上，唯一的症状是"感觉慢"。

### 陷阱 15：只挪代码的重构也能挪动协议

协议由两半拼成：引擎生成的 `capabilities` 和 Swift 解码它的 `Capabilities` 类型。所以一个完全在引擎内部的改动可以破坏契约，而提交信息仍真诚地写着"没有协议改动"。2026-09-10 一次拆分把 `transport_version` 和 `schema_version` 从 `capabilities` 里弄丢了，Swift 侧这两个字段都不是可选的，结果会是拒绝启动（CONTRACT §2）而不是警告。动能力描述或任何回复结构之前，把它打印出来，和 Swift 类型要求的字段对比；两边各有一个测试固定完整的键集合。

### 陷阱 28：自己存了一份约定的校验脚本，会为一个没有节点改动的变化变红

`spk_open` 决定会话的输出色彩空间。三个一致性校验把这个约定写成了常量，而不是从 `open` 回复里读，所以 RFC-018 把输出从 Display P3 改成 ProPhoto RGB 时它们变红了：`parity_render` 27 个用例错 23 个、`parity_grain` 9 级全错、`parity_exposure` 的 c3 全错，而没有任何节点移动、没有任何算术改变。现在它们从 `open` 回复的 `params.io` 读，那是 RFC-018 §5.1 专门为此加的字段。**校验脚本是对引擎做断言的；它对引擎配置的任何认识都必须去问引擎。**

同类的另一个值得单独知道：`parity_schema` 把 `params.hpp` 声明的默认值和 Python 参考实现比较，而参考实现仍声明 sRGB。这个在这里**不可能**变绿（参考实现就是比较对象），所以它带一条登记的 `KNOWN` 差异，形式和 `lens_blur_um` 那条一样：有名字、有理由，**两边若再次一致就失败**。

### 陷阱 35：sidecar 不在照片旁边

很容易这么以为，但自 `06847ab`（2026-09-13）起就不对了：一帧的编辑在 `~/Library/Application Support/SpektraLab/Sidecars/<文件名>-<sha256(路径)前16位>.spektra.json`，带指纹，移动过的文件也能认出来。照片旁的 `<image>.spektra.json` 是**旧家**，第一次读到时会迁移（移动）过去。所以"应用除了导出不往用户文件夹写任何东西"是真的，而在照片文件夹里 `find … -name '*.spektra.json'` 找到的只是残留。缩略图需要的每帧几何在 `open(urls:)` 时从这些文件读进 `Session.savedGeometry`，每帧读一次，和 `frameStates` 共用。

## 5. 测试的可信度

### 陷阱 16：写在纸上的检查，跑在一个它永远不可能触发的配置里

一天之内出现了三次同样的失败，所以它单独成条：

- `deactivate_spatial_effects` 从没把颗粒微结构的高斯模糊半径置零。看不出来，因为唯一测这个开关的测试走的是 `lut_mode`，而它**也**关掉了颗粒：唯一覆盖这个检查的测试，跑在 bug 根本到达不了的地方。
- `Session.warmUp` 用 `try?` 调用 `capabilities`。CONTRACT §2 写着"遇到不认识的传输版本要给出可见错误并拒绝"，却从没实现：客户端解码不了的能力描述，看起来和服务还没启动一模一样。
- 某个测试在一个对 `colour` 的 `xfail` 上面断言"没加载 pandas"，而只要装了 pandas，加载 colour 就**蕴含**加载 pandas。它只在没装 pandas 的环境里通过，也就是产品不用的那个环境。

要找的形状：**一个守卫唯一的被测场景，恰好是被守对象已经关掉的配置。**问一句通过的测试的输入有什么共同点（与陷阱 11 同一个问题）。

### 陷阱 24：测试不拥有 `UserDefaults.standard`，前一个测试类才拥有

应用的持久设置是整个测试进程共享的一个对象，一个测试类写的值就是下一个类读到的值。

- 2026-09-12：`DiagnosticsTests.testADevelopEmitsTheExpectedRecords` 断言 1 MP 冒烟图"恰好一条渲染记录"，这只在预览分辨率大于该帧 1200 px 长边时成立。单独跑这个类是绿的；在一个把预览长边调低的类后面跑整套就出现两条记录，第二条是一次**正确的**原分辨率渲染。测试对代码没错，错的是对输入的假设。出事的是 `ui2.previewLongEdge`，它在会话开始时读取并改变应用渲染什么；`ui2.*`、`diag.*` 下的任何键都一样。
- 一小时内的第二例更糟：一个折叠动画测试读到了别人 `defaults write` 实验留下的 `ui2.leftCollapsed`，面板已经折叠，折叠是空操作，测试**测到的一切都是零并报告成功**。错的计数会大声失败；对象根本没发生的测试会安静通过，与陷阱 16 同族。
- 2026-09-14 又两例，而且都指向了错误的文件：设置 `UserDefaults.argumentDomain` 的测试清不掉它（`removeVolatileDomain(forName:)` 不起作用），`ui2.previewLongEdge` 在进程余下时间都停在 8192，三个类之后另一个测试失败；`FrontendPolicyTests` 断言新 `Session` 的预览长边等于默认值，这是对**机器**的断言，它在 1200 上失败，那是另一个被中途杀掉的运行留在存储里的值。

规则：**依赖持久设置的测试根本不要读共享存储。**注入一个一次性的 `UserDefaults` 套件（`Session.previewEdge(in:)`、`PanelWidthStore` 都支持）。"设置再恢复"在运行被中断前都有效；注入则无法被中断成泄漏，因为没有共享的东西可漏。它总是花掉几小时而不是几分钟，原因在诊断：失败的测试的名字、内容、类都不提那个弄坏它的设置。

### 陷阱 25：`@Observable` 里给自己赋值的 `didSet` 会无限递归

2026-09-12 在 `Diagnostics` 里实测，代价是整个测试进程而不是一个断言。写有界设置最顺手的写法：

```swift
var days: Int {
    didSet {
        days = days.clamped(to: 0...365)      // ← 无限递归
        defaults.set(days, forKey: key)
    }
}
```

`@Observable` 宏把存储属性改写成计算属性，编译器"在属性自己的观察器里赋值不会重入"的规则在改写后不再成立：`setter → didSet → setter → …` 直到栈耗尽，xctest 以 SIGSEGV 死掉。在应用里，同样的属性会在第一次编辑时让设置页崩溃。

自赋值的观察器**只有在能到达不动点时才安全**：`Session.comparePosition` 给自己赋值没问题，因为第二次已经在范围内。要写之前先问：什么让第二次成为空操作？答案是"没有"的话，改成"私有存储属性 + 计算属性、在 setter 里夹紧"，`Diagnostics` 的四个数字现在就是这么写的。

**树里已经有一个擦边的**：`Canvas/Renderer.swift` 对 `comparePosition` 有同样无条件的自赋值，它之所以安全，只因为 `Renderer` 是普通 `NSObject` 子类而不是 `@Observable`。如果有人把 `Renderer` 改成可观察的（它是候选：视图目前通过手写镜像读它），那一行会让进程崩溃，请在同一提交里把它改成计算属性。

另外两点：只在默认值下被用过的设置属性等于没被用过（这个崩溃是被一个赋了越界值的测试发现的）；栈溢出是**崩溃**不是失败，测试运行会重启，报告要读成"有测试没跑完"。

### 陷阱 26：跳过一半的套件和完整的套件都报告 0 失败

相机测试图片不在本仓库，而在 `spektrafilm` 上游里；`tests/Test_image/` 在这里被忽略。每份检出通过一个 `tests` 符号链接拿到它们，**而这个链接在每份检出里正确的目标都不同**：git 工作树指向主检出，主检出指向 `../spektrafilm`。没有链接的检出会跳过依赖图片的用例，只在一行没人看的输出里提一句。

2026-09-14 实测：**18 s、跳过 25 个**对比 **375 s、跳过 0 个**，**都**报告 0 失败。那 25 个里包括承载 RFC-018 §7.2 和 §7.6 的用例，也就是整轮色彩工作所依据的两项测量，于是"已落实为测试"在整整一轮里都是空的，而没人注意到。

**看耗时，不看失败数。**完整运行要几分钟，不到一分钟说明图片不在。`git check-ignore -v tests` 应输出 `.gitignore:/tests`，`ls tests/Test_image/A7m3` 应列出 ARW 文件。这个链接被忽略而不仅是未跟踪，正因为它有三种不同的正确内容，没法"小心地提交"，只能不提交。它曾被一次 `git add -A` 提交过，结果在主检出里指向了自己。

### 陷阱 33：单元都对，不等于界面对

导航器在 1.1.0 发布时，裁切后显示的是**未裁切**的照片，而所有测试都是绿的。没有哪个单元有错：缩略图是对的缩略图，几何是对的几何；只是这个界面从和画布不同的来源读图，组件测试看不到这一点。随后的审计马上又发现一个：画布**直方图**统计的是未裁切的打印，因为 `Renderer.encodeHistogram` 读的是 Layer 2 纹理，几何只在画布采样时才应用。它被固定住而没被修（`XCTExpectFailure(strict: true)`，修好那天测试变红，届时去掉标记）。

规则：**每个显示画面的界面都必须显示画布的画面**，测试方法是给帧加一个裁切**和**一次 90° 旋转，读这个界面，和画布比较：`SpektrafilmTests/SurfaceAgreementTests.swift`。新的面板、读数、文件或 agent 工具只要显示画面，就在那里加一个用例。`ARCHITECTURE.md` §7.7 是"哪个界面显示什么、为什么胶片条故意和导航器不同"的表。

## 6. 应用交互

### 陷阱 29：`kCGImageDestinationEmbedThumbnail` 对 TIFF 不起作用

2026-09-14 实测：带和不带这个选项写出的 TIFF **逐字节相同**（都是 2,883,534 字节，`CGImageSourceGetCount` = 1）。TIFF 真正的机制是第二页，也就是第二次 `CGImageDestinationAddImage`。读的那一半才咬人，因为它失败得**很像成功**：`CGImageSourceCreateThumbnailAtIndex` 找**不到**第二页，而是返回第 0 页的 2048 px 缩图，代价和没有预览一样。看起来能用，显示的却是另一张图，尺寸断言也分辨不出来。预览必须按索引读：`CGImageSourceCreateImageAtIndex(src, 1, nil)`。`ExportPreviewTests` 写一个两页颜色故意不同的 TIFF（只有这样测试才能分辨真的第 1 页和第 0 页的缩图）；`ExportPreviewChainTests` 走真实导出，两页必然是同一张图，所以靠长边区分。两个测试都不能单独成立，注释里都说明了。

### 陷阱 32：AppKit 先把按键给菜单，再给获得焦点的文本框

2026-09-26 用一个裸 `NSMenu` 和一个 `NSTextField` 实测：不带修饰键的 **←** 作为菜单快捷键，在文本框有焦点时也会触发，光标不动。应用的 Capture One 风格快捷键正是这样（←/→ 切帧），于是给配方改名时按 ← 会切换照片。同一个实验里普通字母恰好到达了文本框，但没有任何保证，而且 SwiftUI 自己构建菜单项。修复是 `Windows/TypingKeyGuard.swift`：一个本地按键监听，在询问菜单之前把打字键（字符、方向键、删除）直接交给获得焦点的可编辑 `NSTextView`，把 ⌘/⌃ 组合以及 Return、Enter、Esc、Tab 留给菜单。**加单键快捷键不需要额外工作**；去掉监听 bug 就回来，`TypingKeyGuardTests` 有一个能显示它的对照。画布自己的 `keyDown`（`MetalCanvasView`）早有保护，菜单没有：两条按键路径，只查了一条，与陷阱 16 同形。

### 陷阱 34：导出器写的是当前打开的那一帧

`Exporter.export` 读 `session.selection`；批量导出用 `select` 依次打开每一帧。到 2026-09-26 为止，没有什么能阻止一次点击、一个方向键或一次 agent 调用在循环的 `select` 和写文件之间移动当前帧，结果是把一帧的渲染写进另一帧的文件名。现在由 `Session.batchExporting` 锁住：`click`、`open(_:)`、`togglePick`、`open(urls:)` 和撤销都是空操作，编辑器不接受点击，碰帧的 agent 工具被拒绝。**任何新的、代替用户改变当前帧的操作都必须检查 `batchExporting`**；`select` 本身不能检查，因为它是导出循环自己的门。
